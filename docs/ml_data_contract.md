# VoltEZ ML Data Contract

Status: design only
Models: Demand Forecasting and Charger Availability Prediction
Initial city: Pune
Primary time bucket: 15 minutes
Local training machine: Apple Silicon M4 with 16 GB RAM

## 1. Why 15-minute buckets

A 15-minute bucket is the recommended primary grain because it is:

- responsive enough for charging decisions and host dashboards;
- aligned with frequent prediction refreshes;
- easy to combine into 30-minute, 1-hour, 2-hour, and 6-hour views;
- less sparse than 5-minute buckets for a new marketplace;
- more actionable than using only hourly buckets.

The first generator will create 15-minute rows. Model 1 will predict the following horizons:

- 15 minutes
- 30 minutes
- 60 minutes
- 120 minutes
- 360 minutes

When the system has little data, the model may predict at zone level and the interface may aggregate or smooth adjacent buckets.

## 2. Shared ML rules

1. A prediction has a `prediction_origin`, `feature_cutoff`, and `target_time`.
2. Every feature must have been knowable no later than the feature cutoff.
3. Training data is split chronologically. Random train/test splits are not used for headline evaluation.
4. Synthetic and real data are evaluated separately.
5. All preprocessing is stored with the trained model artifact.
6. Every advanced model is compared against a simple baseline.
7. Unknown labels remain unknown.
8. The application keeps a deterministic fallback for each model.
9. The model output includes version, freshness, interval or calibrated probability, and fallback status.
10. Personally identifying fields never enter the feature set.

## 3. Source snapshots

Every generated training dataset receives a manifest containing:

- snapshot ID;
- source type: synthetic or real;
- source table or file versions;
- generator version and seed for synthetic data;
- covered city and time range;
- row counts;
- schema hash;
- feature view version;
- label definition version;
- creation timestamp;
- code commit when available.

This manifest makes a training result reproducible and prevents accidental comparison of incompatible datasets.

## 4. Model 1: Demand Forecasting

### 4.1 Product question

How many genuine charging requests will occur in a Pune zone during a future 15-minute bucket?

The model powers:

- demand heatmaps;
- predicted congestion indicators;
- host off-peak opportunity windows;
- supply planning;
- a contextual input to Model 2 and the charger ranker.

### 4.2 Prediction grain

One row represents:

`zone_id x prediction_origin x target_bucket x forecast_horizon`

Example:

- Zone: Pune zone A
- Prediction origin: 13:00
- Target bucket: 14:00 to 14:15
- Horizon: 60 minutes
- Label: number of eligible requests created during 14:00 to 14:15

### 4.3 Primary and secondary labels

Primary label:

`request_count`

This counts valid nearby-search, route-planning, and scheduled-search requests whose requested or intended charging location maps to the zone and whose target time falls in the bucket.

Secondary labels used for analysis, not as replacements:

- `served_request_count`
- `no_candidate_count`
- `booking_count`
- `completed_session_count`

Why bookings are not the primary label:

A booking only exists when VoltEZ has a suitable charger and the driver continues. If ten drivers search but only two find a charger, using bookings would report demand as two and hide eight unmet requests.

### 4.4 Request eligibility

Exclude:

- internal development and automated QA accounts;
- duplicate idempotency retries;
- malformed requests;
- requests outside supported geography;
- known bot or abuse traffic;
- requests cancelled before the platform performed any discovery, if that distinction is reliable.

Do not exclude legitimate requests simply because no charger was available.

### 4.5 Required feature groups

#### Calendar

- local hour represented cyclically;
- day of week;
- weekend flag;
- holiday flag;
- minutes to/from major local events when available;
- forecast horizon.

#### Historical demand

- requests during previous 15, 30, 60, and 360 minutes;
- lag at the same time yesterday;
- lag at the same time seven days ago;
- rolling mean, median, and standard deviation;
- exponentially weighted recent demand;
- no-candidate rate.

#### Supply

- listed compatible ports in the zone;
- declared open ports;
- currently operational ports;
- active and confirmed bookings;
- recent supply changes.

Supply is included because discoverability affects observed demand. The team must remember that it may also reflect platform behavior, not only natural city demand.

#### Spatial

- zone identifier or learned/encoded zone category;
- neighboring-zone recent demand;
- nearby compatible supply;
- distance to major corridors or zone-type features generated by the simulator.

#### Optional context

- rain category;
- temperature category;
- event intensity;
- disruption or traffic class;
- contextual source freshness.

Model 1 must work without these optional fields.

### 4.6 Features that are forbidden

- request count from the target bucket;
- bookings created after the prediction origin;
- sessions completed after the prediction origin;
- future availability or future status reports;
- synthetic latent demand intensity;
- any field derived using the whole day when predicting an earlier time;
- personally identifying information.

### 4.7 Baselines

Baseline A: same zone and time bucket from seven days earlier.
Baseline B: rolling hour-of-week average.
Baseline C: global Poisson regression using only calendar and zone features.

The advanced model must beat a meaningful baseline on future-time data.

### 4.8 First advanced candidates

Recommended order:

1. HistGradientBoosting or a scikit-learn count/regression pipeline for a dependency-light prototype.
2. CatBoost, LightGBM, or XGBoost with a count-aware objective after the dataset and baseline are stable.
3. Quantile or conformal prediction for P10, P50, and P90 uncertainty.

Deep learning is not required for the first version. Tree-based models are usually a better fit for this tabular, mixed-feature dataset and local M4 hardware.

### 4.9 Evaluation

Use rolling chronological folds. Report:

- mean absolute error;
- root mean squared error;
- Poisson deviance when valid;
- weighted absolute percentage error only where denominators are meaningful;
- P90 interval coverage and interval width;
- peak-demand recall;
- error by zone, horizon, weekday/weekend, and demand band.

Initial promotion guideline:

- beat the seasonal baseline by at least 10% weighted MAE on multiple rolling folds;
- keep 90% interval coverage approximately between 85% and 95%;
- avoid catastrophic underperformance in any major Pune zone or horizon.

These values are initial engineering gates and may be revised after observing realistic data volume.

### 4.10 Model output

The output contract contains:

- zone ID;
- prediction origin;
- target bucket;
- horizon;
- P10, P50, and P90 demand;
- model name and version;
- feature cutoff and feature view version;
- generated time;
- fallback flag and reason;
- top approved explanatory factors.

### 4.11 Fallback

Use the historical hour-of-week mean with a wide empirical uncertainty interval. New zones fall back to a citywide or similar-zone prior.

## 5. Model 2: Charger Availability Prediction

### 5.1 Product question

For a compatible and otherwise eligible port, what is the probability that the driver can actually begin using it at the predicted arrival time?

The model helps rank uncertain candidates. It does not override hard application constraints.

### 5.2 Hard filters before the model

A port is removed before ML ranking when it is definitely:

- connector-incompatible;
- unreachable above the driver's reserve SOC;
- outside approved access hours;
- not listed for the requested interval;
- under a known maintenance or fault interval;
- blocked by a confirmed overlapping booking;
- suspended or unverified under application policy.

The model is most valuable for uncertainty remaining after these checks, especially in the no-IoT design.

### 5.3 Prediction grain

One row represents:

`request_id x port_id x prediction_origin x target_arrival_at`

The ETA or scheduled arrival horizon is part of the model input because a port that is free now may not be free in 45 minutes.

### 5.4 Label definition

`label = available` when, at target arrival time:

- the business is accessible;
- the port is operational;
- the port is not occupied by an active session;
- no valid booking or blocked interval prevents use;
- observed evidence indicates the arriving driver could begin service within the defined availability tolerance.

`label = unavailable` when trustworthy reconstruction shows the port was unusable at target arrival.

`label = unknown` when the real state cannot be reconstructed confidently.

Unknown examples:

- no arrival and no trustworthy status evidence;
- conflicting reports without a verified outcome;
- missing event history;
- timestamps too inconsistent to reconstruct state.

Unknown is not equivalent to false.

### 5.5 Label evidence priority

From strongest to weaker evidence:

1. Actual check-in and charging-session start.
2. Verified check-in failure with controlled failure reason.
3. Future IoT event if integrated and trusted.
4. Support-verified status observation.
5. Consistent booking/session reconstruction.
6. Fresh QR/GPS-backed user status report.
7. Fresh owner report.

Low-quality or stale evidence may be useful as an input but insufficient as a training label.

### 5.6 Selection bias warning

Real outcomes will be strongest for chargers drivers selected and visited. Unselected candidates may not have reliable labels. Therefore:

- store every recommendation impression;
- collect independent status reports where possible;
- evaluate selected/visited and broadly observed ports separately;
- do not claim the model understands all unvisited chargers equally well;
- use smoothed cold-start priors for new chargers.

Synthetic data can provide complete ground truth for pipeline testing, but only real observations can validate the production model.

### 5.7 Required feature groups

#### Time and horizon

- local hour and day;
- ETA in minutes;
- target arrival bucket;
- business opening/closing proximity.

#### Booking state known at prediction time

- confirmed bookings overlapping or near ETA;
- active holds with their expiry time;
- reservations scheduled before and after ETA;
- recent cancellation and no-show patterns.

Hard conflicts remain filters even if booking features are also present for analysis.

#### Live and recent session state

- number of compatible ports;
- active sessions;
- elapsed service duration;
- expected remaining duration based only on information available then;
- recent arrivals and queue indicators.

#### Status freshness

- last known port status;
- seconds since last status event;
- status source;
- evidence type;
- expiration state;
- recent agreement or disagreement between reports and outcomes.

#### Reliability history

- smoothed session success rate;
- availability mismatch rate;
- host-attributable cancellation rate;
- recent fault frequency;
- evidence count and age.

Driver no-shows must be separated from charger failures.

#### Demand and context

- Model 1 demand P50 and P90 for the target zone and bucket;
- nearby compatible supply;
- optional weather/event context and freshness.

#### Port and host

- connector type;
- power class;
- charger/site port count;
- business category and access type;
- verification age;
- cold-start indicator.

### 5.8 Features that are forbidden

- realized availability at target time;
- session start or failure recorded after prediction origin;
- status reports ingested after the cutoff;
- final booking outcome when predicting earlier availability;
- model-generated confidence from the same target model used as an input;
- future demand counts;
- exact user identity, email, phone, or payment information.

### 5.9 Baselines

Baseline A: deterministic booking, access-hour, and known-status rules.
Baseline B: historical availability rate by port or charger and hour-of-week with Bayesian smoothing.
Baseline C: logistic regression with horizon, booking state, status age, and smoothed reliability.

### 5.10 First advanced candidates

Recommended order:

1. Calibrated logistic regression for a transparent reference.
2. CatBoost, LightGBM, XGBoost, or HistGradientBoosting classifier.
3. Probability calibration using a later chronological validation window.
4. Survival/time-to-free modeling only after Model 2 and the separate waiting-time model require it.

### 5.11 Evaluation

Report:

- log loss;
- Brier score;
- ROC-AUC;
- precision-recall AUC;
- expected calibration error;
- reliability diagrams;
- precision of the high-confidence-available band;
- recall for unavailable outcomes;
- metrics by ETA horizon, source freshness, charger type, zone, and cold-start status.

Initial promotion guideline:

- improve Brier score and log loss over the smoothed historical baseline;
- keep expected calibration error below approximately 0.05 in controlled synthetic evaluation;
- require at least 90% precision before displaying a high-confidence-available badge;
- do not assign extreme confidence to new chargers with little evidence.

### 5.12 Model output

The output contract contains:

- request ID;
- charger and port IDs;
- prediction origin and target arrival time;
- probability available;
- calibrated confidence band or category;
- model name and version;
- feature cutoff and source freshness;
- evidence count;
- fallback flag and reason;
- top approved explanatory factors.

### 5.13 Fallback

Use deterministic booking/access rules plus a freshness-decayed status score and a Bayesian-smoothed historical reliability prior. When evidence is inadequate, return `unknown` or low confidence instead of pretending the port is available.

## 6. Synthetic generator contract

The generator must create events in causal order:

1. Pune zones and latent zone characteristics.
2. Businesses, recurring and exceptional access hours, amenities, offers, chargers, ports,
   parking spaces, and time-bounded tariffs.
3. Driver and vehicle profiles.
4. Time-varying latent demand intensity.
5. Charging requests.
6. Trips, compatible reachable candidates, trip charger options, and recommendation impressions.
7. Driver selection and booking state transitions.
8. Arrivals, queues, sessions, cancellations, no-shows, and outages.
9. Status reports with source-dependent errors and staleness.
10. Demand buckets and point-in-time feature snapshots.
11. Labels and immutable dataset manifests.

The hidden latent parameters used to generate outcomes are kept in QA-only data and are forbidden from training features.

## 7. Synthetic scenarios

The first version should support:

- normal Pune weekday;
- weekend retail demand;
- localized festival or stadium-event spike;
- monsoon traffic disruption;
- charger outage cluster;
- new charger cold start;
- stale or incorrect owner status reports;
- host off-peak capacity activation;
- missing optional external context.

## 8. Generator invariants

Generation fails if:

- a booking references a missing user, vehicle, or port;
- a vehicle is paired with an incompatible connector;
- active booking intervals overlap on a single port;
- an event violates the booking state machine;
- a session begins before arrival or ends before it starts;
- SOC leaves the 0 to 100 range;
- energy or money becomes negative;
- a driver arrives earlier than request time plus travel time;
- a training feature uses information after its cutoff;
- a synthetic row lacks simulation lineage;
- identical seed and configuration fail to reproduce the same manifest hashes.

## 9. Local M4 training approach

Exact commands will be created in the training setup step, not during this design step.

Current plan:

- use a native Apple Silicon Python environment;
- use vectorized Polars/Pandas and NumPy operations;
- use all performance cores through library thread settings where safe;
- start with scikit-learn and CPU tree models;
- measure runtime and memory before introducing larger dependencies;
- verify current Apple GPU/Metal support for the selected library before enabling it;
- never claim GPU acceleration when a library silently falls back to CPU;
- keep generated datasets sized so they fit comfortably within 16 GB RAM.

For these tabular models, a properly configured M4 CPU is expected to be sufficient for the first training iterations.

## 11. Knowledge-check plan

After each executable module is approved and created, the builder receives a short quiz:

1. Explain the module in plain language.
2. Predict what happens when one important parameter increases.
3. Identify one leakage or realism risk.
4. Interpret one validation failure.
5. Suggest one experiment or improvement.
The next implementation step begins only after the module is reviewed and permission is granted.
